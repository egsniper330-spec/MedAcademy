1. EXECUTIVE SUMMARY
----------------------------------------------------------------
- Current login throttle is a fixed per-IP counter: rateLimit('login:'+ip, 10, 60) in AuthService::login (183-269). One IP can try hundreds of accounts at 10/min total. [SI]

3. ATTACKER-INDUCED DoS: OPTIONS A-F
----------------------------------------------------------------
Threat: attacker knows a student email or phone and guesses passwords to make the account unusable.

A. Global per-account cooldown (all sources). Guessing: high. Distributed: high. DoS resistance: POOR (one IP locks the student everywhere). UX: poor. DB: low. Frontend: none. API: works, but 429 reveals account state.
B. Per-account + per-IP counters, both blocking. Guessing: high. DoS resistance: POOR (per-account counter still hits the student). UX: poor. DB: medium. Frontend: minimal.
C. Risk scoring with IP reputation / prefix. Guessing: medium. DoS resistance: medium (NAT false positives). DB: high (needs data). Frontend: minimal.
D. Delay only the (source, account) pair, short capped cooldown. Guessing: high for single-source. Distributed: medium (attacker gets a new source). DoS resistance: GOOD (student unaffected from other sources). UX: good. DB: medium. Frontend: none. API: works.
E. CAPTCHA / step-up after sustained failures. Guessing: high. DoS resistance: good. UX: medium. DB: high (provider, UI). Frontend: REQUIRED. API: needs new response field.
F. Temporary challenge instead of block. Guessing: high. DoS resistance: good. UX: medium. Frontend: REQUIRED. API: needs new response shape.

[R] Use D first. Keep the per-IP limiter (F5) as the throughput cap. Defer E/F until frontend work is approved.

What happens under D [R]:
- Same IP, one account: that pair is delayed. Student from another IP: not delayed.
- Several IPs, one account: each pair has its own delay. Global IP limiter bounds total guessing. No account-wide lock.
- One IP, hundreds of accounts: per-IP limiter caps throughput. Each pair stays short-delayed. Add per-IP alerting.
- Student changes network or uses mobile data: new pair, no delay. Attacker history does not follow the student.
- Student mistypes several times: short delay on that pair that expires. Successful login clears the pair.

Honest limit: a distributed attacker rotating sources, combined with a student on a shared NAT address, is bounded by the IP limiter only. A challenge (E/F) is the only stronger lever, and it needs frontend work.

4. ACCOUNT IDENTITY AND ANTI-ENUMERATION
----------------------------------------------------------------
Identifier formats [SI, AuthService 535-560]: public ID (exact match first), email (case-insensitive on users and profiles), phone (raw users.phone, profiles.phone_e164, profiles.phone). Input is trimmed only. [UNRESOLVED] full phone normalization.

[R] Key strategy: key the throttle on the normalized submitted identifier string, not on user_id. Normalize: trim; lowercase emails; keep public ID as-is; for phone use the same normalizer as resolveIdentifier. Hash the key with SHA-256 (no raw email or phone at rest). Unknown accounts then get the same counter behavior as known ones, so no timing or 429 difference reveals existence.
Limit: aliases that resolve to the same account (email vs phone) get separate counters. Accepted; the global per-IP limiter still applies.

Anti-enumeration rules [R]:
1. Same 401 body and error code for all credential failures (already true: F2, F3).
2. Throttle response must not reveal account state. Use the same 429 code and body for known and unknown identifiers.
3. Retry-After is only sent when the throttle applied to the submitted pair, which is the same for known and unknown.
4. Timing: do not claim equivalence without a measurement plan [NR]. Measure before release.

5. PROGRESSIVE BACKOFF: ALGORITHM [R]
----------------------------------------------------------------
The earlier schedule (failures 1-5 free, 30s, 2m, 10m, cap 15m) is NOT approved. Reasons: 10m and 15m delays are too long for students and still give repeated disruption to the attacker-chosen pair. Doctors and admins should get the same pair rule, with a lower threshold if approved.

Proposed schedule (for approval, see section 13): failures 1-4 free; 5th and later: delay = min(2^(n-4) * 15s, 5min). Cap 5 minutes per pair. Successful login clears the pair.

Rules:
- Failure while a delay is active does NOT extend the delay. The counter increments only when the attempt is actually evaluated (not blocked).
- Counter resets after 24h with no failure (decay).
- Successful login clears the pair row.
- Password reset (F13) clears all pair rows for the target account (needs a per-account key or a scan; see section 6).
- Privileged accounts: same algorithm; a separate, lower threshold may be approved. No MFA in this phase.

Pseudocode:

function loginGate(ip, identifierKey):
  pair = key(ip, identifierKey)
  row = SELECT fail_count, next_allowed_at FROM login_pair_state WHERE pair_key = pair
  if row and row.next_allowed_at > now:
      return THROTTLED(retry_after = row.next_allowed_at - now)   // no counter increment
  return ALLOWED

function recordFailure(ip, identifierKey):
  UPSERT login_pair_state(pair_key, fail_count=1, last_failure_at=now, next_allowed_at=null)
    ON DUPLICATE KEY UPDATE
      fail_count = IF(last_failure_at < now - 24h, 1, fail_count + 1),
      last_failure_at = now
  // next_allowed_at set in the same statement from the new fail_count, only when fail_count >= 5
  // Concurrency: single-row UPSERT inside one statement; no read-modify-write in PHP.

function recordSuccess(ip, identifierKey):
  DELETE FROM login_pair_state WHERE pair_key = pair

DB failure: if the state table is unavailable, fail OPEN for the pair check (allow the attempt), keep the existing per-IP limiter as the hard guard, and log an error. Reason: a temporary security feature must never become a login outage.

Concurrency: two concurrent failures may both increment; the UPSERT keeps the count consistent. Two concurrent successes and failures on one pair: the success deletes the row; a failure that lands after it starts a new count of 1. Acceptable.

6. DATABASE DESIGN DECISION
----------------------------------------------------------------
Option A - reuse rate_limits: fixed-window semantics (F6, F15). Cannot express next_allowed_at or 24h decay without overloading the window column. REJECTED for backoff. Keep it for the IP limiter.

Option B - new login_pair_state table (CHOSEN [R]). Only fields needed:
- pair_key CHAR(64) NOT NULL PRIMARY KEY (SHA-256 of ip + normalized identifier, hashed).
- fail_count INT NOT NULL DEFAULT 0.
- last_failure_at DATETIME(6) NOT NULL.
- next_allowed_at DATETIME(6) NULL.
Not needed: user_id (privacy and unknown accounts), raw ip (hashed in pair_key), created_at/updated_at (last_failure_at is enough).
Indexes: primary key only; cleanup uses last_failure_at (add INDEX on last_failure_at).
Additive migration only. Does not alter login_history or rate_limits.

Option C - separate per-IP and per-account tables: REJECTED. Per-IP is already covered by rate_limits (F5). Per-account blocking is the attack vector.

Cleanup [R]: delete rows where last_failure_at < now - 24h, in batches. No repo job exists today (F17), so a new job is required and is part of Package B.

Privacy: no raw identifier or IP stored. Account deletion: rows expire within 24h; no FK to profiles needed.

Schema SQL (proposal only, NOT written, NOT executed):
  CREATE TABLE login_pair_state (
    pair_key CHAR(64) NOT NULL PRIMARY KEY,
    fail_count INT NOT NULL DEFAULT 0,
    last_failure_at DATETIME(6) NOT NULL,
    next_allowed_at DATETIME(6) NULL,
    INDEX idx_lps_last_failure (last_failure_at)
  ) ENGINE=InnoDB DEFAULT CHARSET=utf8mb4 COLLATE=utf8mb4_unicode_ci;

7. IMPLEMENTED CONTROL (Phase 1A)
- Per-IP limiter unchanged: rateLimit('login:'+ip, 10, 60).
- Pair throttle keyed on HMAC-SHA256(LOGIN_THROTTLE_HMAC_KEY, ip + '|' + normalized identifier).
- Check runs before identifier resolution and password verification; read-only, so refused attempts never extend a cooldown.
- Failure is one atomic upsert; a cooldown already in force is kept.
- Success clears the pair row. Unknown and known identifiers take the same path.
- Missing HMAC key disables only the pair throttle; the per-IP limiter still applies.

8. ANTI-ENUMERATION (as implemented)
- Same 429 body (code rate_limited) for known and unknown identifiers.
- Retry-After is sent only when the submitted pair is in cooldown.
- Unknown-account failures write no login_history row (existing behaviour).

9. PASSWORD RESET LIMITATION [NR]
- login_pair_state stores no user_id, so reset cannot find or delete pair rows.
- Mitigation is bounded expiry: stale rows reset after 24h and are purged by the cron script.
- A reset does not lift an active pair cooldown until it expires (max 300s by default).
