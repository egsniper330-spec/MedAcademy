1. EXECUTIVE SUMMARY
==================================================================

- Phase 0 (telemetry and logging accuracy) is ready for a short design step
  and then small code changes. The changes must not alter any enforcement
  decision.
- Phase 1A (per-account login protection) is NOT ready for implementation.
  Login has only a per-IP limiter. There is no per-account failure state.
  A naive per-account lock would let one attacker lock any student out, so
  the algorithm must be approved first (section 5).
- Correction to the earlier report: unknown accounts do NOT create a
  "no_account" login_history row. [SI] recordLogin() returns early when
  $userId is null, and login_history.user_id is NOT NULL. Failed attempts
  against unknown accounts are visible only in the per-IP counter in
  rate_limits.
- Recommendation: approve Phase 0 design now. Hold Phase 1A until the
  decisions in section 13 are made.

3. PHASE 0 FINDINGS AND RECOMMENDATIONS
==================================================================

3.1 Logging accuracy [SI]

  a) IntegrityService::reject() logs policy_action = "log_only" even when
     the policy would block. Fix: log the policy's real action. Do not change
     the decision.
  b) SecurityEvidenceService::assertEvidenceAllowed() (~567-620) logs
     "block_login" for every action, even non-login actions. Fix: log the
     action's own configured policy.
  c) [R] Add an explicit enforcement_mode column or field ("log_only" or
     "enforce") so the label cannot be confused with the decision.
  d) Constraint: security_events.policy_action has a CHECK constraint
     (schema.sql ~1524) allowing only log_only, warn_only, block_video,
     block_login. Any new value needs a migration. Do not add values silently.

3.2 Telemetry coverage

  Metric                                       Derivable today?
  -------------------------------------------  --------------------------------
  Integrity verdicts per action                Partly. play_integrity_verdicts
                                               exists (017). Action column
                                               must be confirmed. [NR]
  TRUSTED / DEGRADED / UNTRUSTED distribution  Only if security_evidence stores
                                               the tier (018). Confirm. [NR]
  Missing / invalid / expired / replayed       Partly, via failure_reason
    evidence                                   strings. Not a stable enum.
  Google outage vs negative verdict            Not separated. [R] add an
                                               explicit upstream_error reason.
  Device key status and promotion              Partly. device_keys (018) plus
                                               verified_at and
                                               verification_note (019).
  Login failures per account                   Known accounts only, as
                                               login_history rows.

  [R] Minimum additions, all additive: a stable failure_reason enum for new
  events, enforcement_mode, and a request_id for correlation.

3.3 Privacy [SI] [R]

  - Confirm no new code path stores passwords, JWTs, refresh tokens, or raw
    attestation tokens.
  - ip_address is stored as TEXT today with no retention rule. [A] [R] set
    90 days for login and failure rows and 180 days for security events,
    with a named owner.
  - [R] Hash device identifiers in new telemetry if clear values are not needed.
  - [R] Restrict telemetry export to super_admin, and audit every export.

3.4 Baseline measurement [R]

  - Read-only queries over security_events, play_integrity_verdicts,
    security_evidence, and login_history can produce counts per action and
    per reason, plus unique accounts and devices.
  - A false-positive rate cannot be derived from stored data. There is no
    ground-truth label. Report only "rejections later overridden", which
    needs a new field. Do not estimate it.
  - An additive migration is needed only for enforcement_mode and the new
    reason enum.

3.5 Phase 0 acceptance criteria [R]

  1. Integrity rejection under log_only logs policy_action=log_only and
     enforcement_mode=log_only.
  2. Same rejection under enforce logs enforce and returns the same blocked
     response as today (golden test).
  3. A non-login evidence rejection never logs block_login.
  4. No telemetry row contains a password, token, or raw attestation payload
     (fixture assertion).
  5. The baseline query matches a manual count on a seeded fixture.
  6. Enforcement responses are byte-identical before and after.

5. RECOMMENDED ACCOUNT PROTECTION ALGORITHM
==================================================================

5.1 Options compared [R]

  1. Hard lock after N failures ........ REJECTED. Any attacker can lock any
                                         account out.
  2. Progressive delay per account ..... RECOMMENDED as the base. Temporary,
                                         capped.
  3. IP throttling plus risk score ..... RECOMMENDED as a companion.
  4. CAPTCHA after suspicion ........... DEFER. Adds a frontend contract.
  5. Temporary challenge flow .......... DEFER until a challenge flow exists.

5.2 Proposed values [A] (need approval)

  - Failures 1-5: no delay.
  - Failure 6: 30 s. Failure 7: 2 min. Failure 8: 10 min. Cap: 15 min.
  - A successful login clears the account state.
  - A failure during an active delay does not extend it.

5.3 Where it applies [R]

  - After the account is found AND the password is checked, so unknown and
    wrong-password requests take the same path.
  - The delay response is the same generic 401 body and the same timing.
    Send Retry-After only for the wall-clock wait.

5.4 Open concern: account existence leak

  A 429 for a known account but a 401 for an unknown one reveals which
  accounts exist. [R] Either return the same 429 for both once the key has
  history, or add a fixed minimum response time on every login. The second
  option adds latency for every user. This needs a decision (section 13).

6. DATABASE AND MIGRATION PROPOSAL
==================================================================

6.1 Preferred: reuse rate_limits [R]

  - New operation name, e.g. login_account, keyed by a normalized account key
    (lowercased resolved user_id, not the raw typed identifier).
  - Fits the existing UNIQUE key and atomic INSERT ... ON DUPLICATE KEY UPDATE.
    [SI] schema.sql 656-669; RateLimitService::hit() 68-98.
  - No new table required.

6.2 Limit of reuse [SI] [R]

  Fixed windows cannot express "wait 30 s after the 5th failure". The
  per-account state needs a last-failure timestamp and a failure count that
  reset on success. Options:
    a) Add columns to a new table account_login_state (user_id PK, failure_count,
       last_failure_at, locked_until). Preferred for clarity.
    b) Encode state in rate_limits rows. Works but is harder to read.

6.3 Proposed migration (not written) [A]

  - Migration number: next free after 039, to be confirmed.
  - Additive only. No change to login_history, rate_limits, or security_events
    rows.
  - Index on last_failure_at for cleanup.

6.4 Cleanup [R]

  - Delete state rows older than 24 h with no active delay.
  - Run from an existing maintenance path, not a new cron.
