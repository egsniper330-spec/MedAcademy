==============================================================
1. EXECUTIVE SUMMARY
==============================================================

- Common root cause [SI]: the enforcement machinery for Play Integrity and device evidence is built, but the default policy keeps it in log_only. Results are recorded but do not block. Most remaining work is policy, verification and rollout, not new cryptography.
- Play Integrity [SI]: IntegrityService::policy() defaults all five actions to log_only with enabled=false. Tokens are fully verified, but a failure does not stop the action.
- Device evidence [SI]: SecurityEvidenceService::policy() defaults to log_only. require_registered_key defaults to false and only lowers the tier to DEGRADED. It never blocks on its own.
- iOS App Attest [SI][AT]: the 503 is intentional. docs/PRODUCTION_READINESS_AUDIT.md section 8 defers App Attest, and tests/appAttestDeferral.test.cjs checks that deferral. Client code exists, but there is no server verifier and no App Attest entitlement. This is an accepted gap, not a regression.
- MFA [SI]: no TOTP, recovery-code or MFA tables or code exist in backend/src or migrations 015-020. The prior audit finding is correct.
- Lockout [SI]: login throttling is per IP only (rateLimit('login:'+ip, RATE_LIMIT_LOGIN_PER_MINUTE=10, 60) in AuthService::login()). There is no per-account failure counter, lockout or backoff.
- Recommendation [R]: do not flip every log_only to enforce. Choose a verdict per action after a measured baseline. The best first step is per-account login protection, which does not depend on device signals and has low false-positive risk.

CORRECTION TO THE PRIOR AUDIT [SI]
The Play Integrity request hash does not bind operation parameters. It binds the user, the action and a single-use server nonce. The client requests the hash before it knows the video or PDF ID, so a valid token can be replayed against a different resource within verdict_ttl_seconds (60-900). Device evidence hashes the request body and is the control that binds the exact operation.

Login through the web preview is statically verified only [NR]. Not deployed; needs your approval.

3. PLAY INTEGRITY DETAILED ASSESSMENT
==============================================================

3.1 Flow [SI]
1. get_nonce (src/lib/integrityClient.ts ~70-72) returns a single-use 256-bit request_hash bound to (user, action).
2. The native module requests a Play token with that hash as the classic nonce (src/lib/nativeSecurity.ts ~774).
3. verify (IntegrityService::verifyToken()) decodes the token via Google. It checks nonce single-use and expiry, package name, hash_equals on the request hash, timestamp (10 min, 60 s skew), PLAY_RECOGNIZED, certificate pin, device verdict, and licensing (off by default).
4. Google outage: decodeWithGoogle() returns 503 on outage and 403 on 4xx. The rejection is persisted, but policy does not block.

3.2 Per-action analysis

Action        | Why log_only | Reaches authz? | Missing attestation | Replay / staleness               | Recommended verdict
--------------|--------------|----------------|---------------------|-----------------------------------|----------------------------------------------------------
vdo_otp       | default      | No             | Allowed             | Nonce single-use; verdict reusable within TTL | PLAY_RECOGNIZED + MEETS_BASIC_INTEGRITY. Phase 2.
material_pdf  | default      | No             | Allowed             | Same                              | Same, enforced after vdo_otp.
redeem        | default      | No             | Allowed             | Same                              | PLAY_RECOGNIZED only at first. Brute-force protection (section 7) matters more.
device_bind   | default      | No             | Allowed             | Same                              | Keep log_only until section 4 is confirmed. Then MEETS_BASIC_INTEGRITY only.
financial     | default      | No             | Allowed             | Same                              | MEETS_DEVICE_INTEGRITY + step-up MFA (section 6). Not attestation alone.

Hash binding, all actions: user + action + nonce, not the video or PDF ID.
Repackaging [SI]: package name and cert pin cover re-signed builds. A release-key rotation without updating the pin would block all users. [R] Keep the pin in config and check it in CI before enforcement.
Google outage [R]: do not enforce on a Google 503 alone. Add a google_unavailable decision that falls back to device evidence and is logged as a degraded state.
False positives [A]: rooted and older devices are the main risk for MEETS_DEVICE_INTEGRITY. Baseline data (section 11) should decide the final verdict.

4. DEVICE EVIDENCE DETAILED ASSESSMENT
==============================================================

4.1 Key generation and hardware backing
- Keys are generated in Android Keystore (plugins/withSecurityModule.js ~2579-2706). StrongBox is requested with fallback (~2610).
- deviceKeySecurityLevel() returns tee or software (~2643-2651). This value goes to the client only. No server-side check requires tee or StrongBox. [SI]
- Whether production devices produce hardware-backed keys is not confirmed. [NR]

4.2 Registration and authentication
- issueChallenge() requires an active devices row, so a key cannot be registered for an unknown device. [SI]
- Abuse path: registering a new key for an existing device. The 24 h warm-up limits its effect on protected actions. I did not confirm that new key registration requires a fresh session or step-up. [A]
- [R] Require step-up MFA (section 6) before registering a new key on an existing device.

4.3 Counter, signatures and rollback
- Counter must strictly increase, with a gap cap of 1000 (min_counter_gap). Signatures are ECDSA P-256 over canonical JSON. [SI]
- Rollback: restoring an old app-data backup gives an older counter. The server rejects it, so the user is locked out of enforced actions until the key is re-registered. [A] Re-registration should be a defined recovery path.
- Challenges are single-use, user-bound, action-bound, device-bound, session-bound and request-hash-bound. [SI]

4.4 Revocation
- Keys of a revoked device remain in device_keys until status changes. Verify that revoking a device sets the key inactive in the same transaction. [A] Not yet confirmed.

4.5 Enforcement path
- assertEvidenceAllowed() returns early unless the tier is enforce or enforce_strict. enforce_strict requires TRUSTED. Rejected integrity rows are always denied. [SI]
- Call sites: VideoController (~74, 84, 139, 146); MaterialDeliveryController (~121); RedeemCodeController (~357, 366); DeviceController (~74, 83); SecurityEvidenceController (~121).

4.6 Recommendation [R]
- Enforce device evidence on vdo_otp and material_pdf first (tier enforce, not enforce_strict).
- Keep device_bind on log_only until registration is protected by step-up.
- Do not require tee or StrongBox until baseline data shows the hardware-backed share.

- No Apple Developer credentials in the repo. [A]

5.3 Required implementation (if approved) [R]
- Entitlement: add com.apple.developer.app-attest-environment (production) to ios.entitlements.

6. MFA ARCHITECTURE PROPOSAL
==============================================================

6.1 Current state [SI]: no MFA exists.

6.2 Design [R]
- TOTP (RFC 6238) with a per-user secret encrypted at rest. Enrollment requires a valid current code before activation.
- Ten single-use backup recovery codes, stored as hashes, shown once.
- Step-up: a short-lived 'mfa_verified' claim on the session for sensitive actions (financial, role change, new device key, password change).
- Mandatory for Super Admin and Admin. Mandatory for Doctor accounts that can access protected material [A]. Optional for students.
- Avoid email OTP as the only factor for privileged accounts.

6.3 Interaction with JWT and refresh tokens [R]
- Access token carries mfa_at (auth time) and amr claims. Refresh keeps them; the step-up window is server-side.
- Refresh rotation unchanged. Bump security_version on MFA disable or recovery so existing sessions are revoked.
- Device management: a new device login for a privileged account requires MFA.
- Password reset: revoke sessions; require MFA on next login for privileged accounts.
- Admin permission changes and financial operations require a fresh step-up.

6.4 Recovery [R]
- Recovery codes first. If lost, a second admin with MFA can reset, with an audit event. No self-service reset by email alone for privileged accounts.

==============================================================
7. ACCOUNT LOCKOUT ARCHITECTURE PROPOSAL
==============================================================

7.1 Current state [SI]: IP-only limit of 10 per minute. No per-account failures, lockout or backoff.

7.2 Design [R]
- Per-account failure counter (login_failures table or a column set), keyed by normalized email plus user ID when it exists.
- Progressive backoff: after 5 failures, delay grows (for example 30 s, 2 min, 10 min, capped at 15 min). Lockout is temporary; no permanent lock.
- Track failures per IP and per network prefix so one IP cannot lock an account for everyone. Use a CAPTCHA or step-up challenge instead of a hard lock when risk is high.
- Anti-enumeration: identical response and timing for unknown and known accounts.
- Credential stuffing and spraying: alert when many accounts see one failure from one IP range, or one password across many accounts.
- Audit events: lockout, unlock, suspicious spike. Alert admins on lockouts of privileged accounts.
- Recovery: a verified email reset clears the lock; an admin can unlock with audit.

7.3 Abuse guard [R]
- Lockout must never block the legitimate owner indefinitely. Cap duration and do not let failures from unknown IPs lock accounts forever.

==============================================================
8. UNIFIED SECURITY POLICY DESIGN
==============================================================

8.1 Principle [R]: the PHP backend is authoritative. The client never decides enforcement. Native results are inputs, not verdicts.

8.2 Decision inputs
- Play Integrity verdict (per action, from verdict store).
- Device evidence assurance (TRUSTED / DEGRADED / UNTRUSTED) and integrity history.
- Account state: role, MFA status, step-up freshness, security_version.
- Device state: active, blocked, key status.
- Risk signals: login failure spike, IP reputation (if available).

8.3 Decision outputs
- ALLOW, STEP_UP (require MFA or re-attest), DENY, and DEGRADED_ALLOW (logged, limited to low-risk actions).

8.4 Per-action matrix [R]

Action        | Play Integrity          | Device evidence     | MFA / step-up       | Outage behaviour
--------------|-------------------------|---------------------|---------------------|-----------------------------
vdo_otp       | PLAY_RECOGNIZED         | enforce (TRUSTED or DEGRADED) | none           | DEGRADED_ALLOW with alert
material_pdf  | PLAY_RECOGNIZED         | enforce             | none                | DEGRADED_ALLOW with alert
redeem        | PLAY_RECOGNIZED         | log_only then enforce | none              | Allow with rate limit
device_bind   | log_only                | log_only            | step-up for new key | Allow with alert
financial     | MEETS_DEVICE_INTEGRITY  | enforce_strict      | required            | DENY until restored

8.5 Client rules [R]
- The client sends evidence but does not decide. Local security flags must not skip server checks.
- Suppressing a native detector result must produce the same server outcome as a failure.

8.6 Unsupported devices and upgrades [R]
- Unsupported devices (no Play services, old OS) get DEGRADED, not DENY, for low-risk actions.
- After an app upgrade, the first request may be DEGRADED until integrity history re-anchors.

11. FALSE-POSITIVE AND USER-LOCKOUT RISKS
==============================================================

- Rooted or old devices failing MEETS_DEVICE_INTEGRITY [A]: high impact for financial. Mitigation: step-up, not hard block.
- Certificate pin mismatch after key rotation [SI]: would block all users. Mitigation: pin check in CI and a staged pin list.
- Google outage [A]: could block all protected actions. Mitigation: DEGRADED_ALLOW with alert.
- Device reset or backup restore [A]: old counter causes lockout. Mitigation: defined re-registration path.
- Lockout abuse [R]: a permanent lock is a denial-of-service tool. Mitigation: temporary, capped lockouts and IP-aware counters.
- Student lockout by MFA [R]: optional for students; mandatory only for privileged roles.
- Baseline required [R]: collect at least two weeks of log_only verdicts per action before enforcing.
